# 개발 워크플로

지금까지 정한 개발 방식을 한 문서로 모은 것입니다. 새 작업은 `docs/tasks/`에 작업 지문(md)을 만들어 시작합니다.

## 1. 원칙

- **기능 하나는 모듈 하나다.** 새 기능은 기존 파일에 끼워 넣지 않고, 기능마다 모듈(파일 또는 폴더) 하나로 만듭니다. 기능이 다른 기능과 맞닿는 곳은 **계약**으로 명시합니다(아래 8절).
- **연결은 필요한 것만.** 모듈은 자기가 쓰겠다고 선언한 모듈의 이름만 부를 수 있고, 선언하지 않은 연결은 검사에서 실패합니다.
- **규칙과 검사를 먼저 정한다.** 구조를 먼저 정해 두면 나중에 기능을 붙여도 규칙이 유지됩니다.
- **모듈은 층으로 나누고 의존은 한 방향으로만 흐른다.** 화면 → 모듈 순서로만 부르고, 모듈은 화면·DB·전역 상태를 참조하지 않습니다.
- **모듈은 입력을 받아 결과를 돌려주는 순수 함수로 만든다.** 현재 시각 같은 값은 인자로 받아 테스트가 가능하게 합니다.
- **설계가 확정된 md가 있으면 바로 구현한다.** 설계 확인은 작업 md에서 한 번 받은 것으로 봅니다.

## 2. 층 배치 (기본 틀)

```
[화면 층]   UI, 입력 처리, 렌더링
     │  호출
     ▼
[모듈 층]   도메인 규칙, 계산, 포맷 (순수 함수)
     │  의존하지 않음
     ✕       외부 I/O, DOM, 전역 상태
```

- 모듈 폴더는 `src/modules/<이름>/`에 두고, 외부에서는 `index` 진입점만 가져갑니다.
- 모듈 간 호출이 필요하면 진입점으로만 합니다. 구현 파일끼리 직접 참조하지 않습니다.

## 2-1. 떼어내기 (모듈 재사용)

- 모듈은 "계약 닫힘"으로 떼어 낼 수 있어야 합니다. 떼어낼 모듈이 쓰는 모듈들(계약의 `uses`를 따라간 집합)을 같이 가져가면 됩니다.
- 떼어내기 전에 닫힌 집합을 확인합니다. 집합이 지나치게 크면 계약을 다시 나눕니다.

## 3. 스킬 세트

| 단계 | 스킬 | 역할 |
|------|------|------|
| 설계 | `codebase-design` | 모듈 경계, 의존 방향, 인터페이스 |
| 고치기 전 | `change-impact` | 영향 범위 분석 |
| 구현 | `test-driven-development` | 테스트를 먼저 만들고 구현 |
| 옮긴 뒤 | `module-regression` | 바뀐 기능과 하류 기능 검증 |
| 구조 확인 | `graphify` | 관계도로 설계와 대조 |
| 결정 | `architecture-decision-records` | 선택과 이유 기록 |

호출 순서: 설계 → 영향 분석 → 테스트 → 구현 → 검증 → 관계도 대조. 선택이 생기면 그때마다 ADR을 남깁니다.

## 4. 검사 순서

1. 단위 테스트: 모듈 함수를 직접 호출해 정상 입력, 경계값, 잘못된 입력을 확인
2. 기존 결과와 비교: 바꾸기 전후 출력이 같은지 확인 (바뀌면 이유를 작업 md에 남김)
3. 실행 확인: 화면이 있으면 브라우저에서 열어 콘솔 오류가 없는지 확인
4. 계약 검사: 선언되지 않은 연결이 없는지 확인 (실패 시 계약을 고치거나 연결을 없앰)
5. 연결도: 계약에서 만든 관계도(`docs/MODULES.md`)와 설계가 맞는지 대조하고 보고

검사에 실패하면 실패 출력을 그대로 보고합니다. 통과하지 못한 것을 통과했다고 쓰지 않습니다.

## 4-1. 모듈 계약 (기능과 연결의 명시)

모듈마다 다음 세 가지를 선언합니다. 선언은 코드 밖(매니페스트 등)에 두고, 기능 코드 자체는 바꾸지 않습니다.

- **모듈 이름:** 기능을 가리키는 이름 (예: "출력-ppt")
- **제공 (provides):** 다른 모듈에 내주는 최상위 이름 목록
- **사용 (uses):** 이 모듈이 쓰는 다른 모듈의 **이름** 목록

검사 규칙:
- 계약이 선언된 두 모듈 사이에서, 한 모듈이 다른 모듈의 이름을 부르면 `uses`에 그 모듈이 있고 `provides`에 그 이름이 있어야 합니다. 아니면 실패합니다.
- 계약이 없는 쪽이 끼면 정보로만 보여 줍니다(이행 중).

가시화:
- 계약에서 관계도를 만들어 `docs/MODULES.md`에 둡니다. 계약 연결은 실선, 계약 없이 실제로 부르는 연결은 점선으로 구분합니다.
- 떼어내기 확인 명령으로 닫힌 집합을 출력해 문서에 남깁니다.

## 5. Git 규칙

- 지정된 작업 브랜치에서만 커밋하고 푸시합니다. (`git push -u origin <브랜치>`)
- PR은 요청이 있을 때만 만듭니다.
- 커밋 메시지는 한국어로 쓰고, 마지막 줄에 Claude 공동 작성 표기를 둡니다.

## 6. 작업 시작 방식 (md 킥오프)

1. 작업 지문을 `docs/tasks/<날짜>-<이름>.md`로 저장합니다. 양식은 `docs/tasks/TEMPLATE.md`를 씁니다.
2. 세션에 md를 주면 Claude는 질문 없이 읽고 바로 시작합니다.
3. 아래 경우에만 먼저 묻습니다.
   - 필수 항목(저장소, 목표, 완료 기준)이 비어 있을 때. 저장소가 정해지지 않으면 코드를 만들기 전에 멈춥니다.
   - 되돌리기 어려운 작업(데이터 삭제, 공개 배포, 다른 저장소 쓰기, PR 생성)일 때
   - md에 적힌 저장소가 접근 범위 밖일 때 (새 저장소는 생성 전에 md에 이름과 설정이 있어야 합니다)
4. 끝나면 결과를 md 맨 아래 "결과" 칸에 채우고, 검사 결과와 연결도를 함께 보고합니다.
5. 세션 번호: 같은 작업 ID의 세션이 새로 시작될 때마다 제목을 `<작업 이름> #<N>`으로 붙입니다. 태그(`task:<작업 ID>`)로 세션을 찾고, 도구를 쓸 수 없으면 md의 "세션 기록"에 번호를 적습니다.
