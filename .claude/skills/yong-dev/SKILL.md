# 용개발

개발 작업을 같은 방식으로 시작하고 끝내기 위한 워크플로입니다. 세부 규칙은 `references/` 아래 문서를 따릅니다.

- `references/START_PROMPT.md`: 작업 지문 양식 (사용자가 채움)
- `references/TEMPLATE.md`: 작업 md 저장 양식
- `references/WORKFLOW.md`: 원칙, 층 배치, 검사, Git 규칙
- `references/BUILD_PROMPT.md`: 무엇을 만들지 채우는 지문 (기능, 모듈, 화면, 도구)

## 1. 켜기

"용개발 켜줘"라고 하면 용개발 모드로 진행한다고 알리고, `references/START_PROMPT.md` 양식을 보여 줍니다. 사용자가 양식을 채워 주면 다음 단계로 갑니다.

## 2. 필수 항목 확인

다음 셋이 비어 있으면 코드를 만들기 전에 묻습니다.

- 저장소 (`owner/repo`)와 브랜치. 새 저장소라면 이름과 설정
- 목표
- 완료 기준

## 3. 작업 md 저장

채워진 내용을 `docs/tasks/<날짜>-<작업 ID>.md`로 저장합니다. 양식은 `references/TEMPLATE.md`를 씁니다. 저장 후 바로 시작합니다.

## 3-1. 이어받기 (토큰 때문에 세션을 넘긴 경우)

- 세션 시작 시 상태가 "진행"인 작업 md가 있으면 그 인계 메모가 함께 들어옵니다. 그 작업을 이어서 합니다.
- 이어받는 순서: 인계 메모 읽기 → `git status`와 `git log`로 바꾼 파일 확인 → 인계의 "다시 실행할 명령"으로 현재 상태 확인 → "다음에 할 것"부터 진행.
- 처음부터 다시 만들지 않습니다. 이미 통과한 테스트와 끝난 단계는 건너뜁니다.
- 인계 메모와 실제 상태가 다르면 실제 상태를 기준으로 하고, 다른 점을 먼저 보고합니다.
- 넘길 때는 인계 칸을 채우고 상태를 "진행"으로 둡니다. 끝나면 "완료"로 바꿉니다.

## 4. 세션 번호

같은 작업 ID의 세션이면 제목을 `<작업 이름> #<N>`으로 붙입니다.

1. `set_session_tags`로 `task:<작업 ID>` 태그를 붙입니다.
2. `list_sessions`로 같은 태그의 세션 수를 셉니다. N = 그 수 + 1.
3. `set_session_title`로 제목을 설정합니다.

도구를 쓸 수 없으면 md의 "세션 기록"에 `#N 날짜: 한 일`을 적습니다.

## 5. 개발 순서

1. 설계: `codebase-design`으로 기능 하나를 모듈 하나로 나누고, 모듈마다 제공(provides)과 사용(uses)을 정하기
2. 영향 분석: `change-impact`로 고치기 전 영향 범위 보기 (계약의 uses를 따라 확인)
3. 구현: `test-driven-development`로 테스트를 먼저 만들고 구현. 계약에 없는 연결은 만들지 않기
4. 검증: `module-regression`으로 바뀐 기능과 하류 기능 확인, 계약 검사 통과
5. 구조 대조: 계약에서 `docs/MODULES.md` 관계도를 다시 만들고 설계와 맞는지 보기 (`graphify`는 보조)
6. 떼어내기 확인: 이 모듈을 다른 곳에서 쓸 때 가져갈 닫힌 집합을 기록
7. 결정 기록: 선택이 있었으면 `architecture-decision-records`로 남기기

원칙: 새 기능은 기존 모듈에 끼워 넣지 않고 모듈 하나로 추가합니다. 연결은 계약에 적은 것만 허용합니다. 자세한 규칙은 `references/WORKFLOW.md`의 1절과 4-1절.

층 배치는 화면 → 모듈 한 방향만 허용합니다. 모듈은 순수 함수로 만들고, 현재 시각 같은 값은 인자로 받습니다.

### 5단계 서브에이전트

메인 세션은 저장소, md, 세션 번호, Git을 맡고, 실제 작업은 아래 에이전트에 넘깁니다.

| 번호 | 단계 | 에이전트 | 모델 | 하는 일 | 산출물 |
|------|------|----------|------|---------|--------|
| 1 | 자료 조사와 디자인 | `yong-researcher` | Sonnet | 기존 코드, 문서, 웹 자료를 모으고 방향 후보와 추천을 정리 | `<작업 ID>-research.md` |
| 2 | 설계 | `yong-designer` | Opus | 모듈 경계, 의존 방향, 인터페이스 정하기 | `<작업 ID>-design.md` |
| 3 | 구현 | `yong-builder` | Sonnet | 테스트 먼저 → 실패 확인 → 구현 → 통과 확인 | 코드와 테스트 |
| 4 | 검사 | `yong-checker` | Haiku | 테스트 실행, 전후 비교, 연결도, 의존 위반 확인 (코드 수정 없음) | 검사 출력과 연결도 |
| 5 | 검토와 보고 | `yong-reviewer` | Opus | 1~4번 결과를 의심하며 직접 다시 확인하고 사용자에게 보고 (파일 수정 없음) | 판정 표 |

순서: 1 → 2 → 3 → 4 → 5. 각 단계는 앞 단계 산출물이 있어야 시작합니다.

### 보고와 수정 요청

- **"보고"** 라고 하면 5번 검토 에이전트가 1~4번이 한 일을 단계별로 정리해 보고합니다. 정리가 실제와 맞는지도 함께 확인합니다.
- **마음에 들지 않는 부분**을 말하면 5번이 어느 단계의 문제인지 밝히고, 그 단계에 줄 명령을 알려 줍니다. 명령은 바로 실행하지 않고, 사용자가 승인하면 메인 세션이 해당 단계에 넘깁니다.

### 수정 루프

5번이 고칠 단계를 정하면, 메인 세션은 해당 단계에만 명령을 줍니다.

- 자료가 틀렸으면 1번부터 다시 (`yong-researcher`)
- 설계가 틀렸으면 2번부터 다시 (`yong-designer`), 이후 3·4·5번 재실행
- 구현이 틀렸으면 3번부터 다시 (`yong-builder`), 이후 4·5번 재실행
- 검사가 부족했으면 4번만 다시 (`yong-checker`), 이후 5번 재실행

고친 뒤에는 반드시 5번 검토를 다시 돌립니다. 검토 판정이 모두 "맞음"이 되기 전에는 완료로 보고하지 않습니다.

- 검사 에이전트의 보고는 그대로 md의 "결과" 칸에 옮깁니다.
- 에이전트 정의는 `.claude/agents/`에 있습니다. 다른 프로젝트로 옮길 때는 이 폴더도 함께 복사합니다.

## 6. 검사와 보고

- 단위 테스트, 바꾸기 전후 출력 비교, 화면이 있으면 실행 확인을 합니다.
- 실패한 출력은 그대로 보고합니다. 통과하지 못한 것을 통과했다고 쓰지 않습니다.
- 끝나면 md의 "결과" 칸을 채우고, 변경 파일과 검사 출력, 연결도를 보고합니다.

## 7. Git

- 지정된 브랜치에만 커밋하고 `git push -u origin <브랜치>`로 푸시합니다.
- PR은 요청이 있을 때만 만듭니다.
- 되돌리기 어려운 작업(데이터 삭제, 공개 배포, 다른 저장소 쓰기, PR 생성)은 먼저 확인합니다.
